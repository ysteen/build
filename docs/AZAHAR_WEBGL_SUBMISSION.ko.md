# Azahar 광장 장면의 WebGL 처리 최적화

대상: 8081 RomM 테스트 서버, 2026-09-23.

사용자가 만든 RomM 상태 **29번**으로 광장을 복원해 비교했습니다.
요청한 두 항목인 반복 GPU 업로드 재사용과 WebGL 호출 경로 단축을 적용했습니다.
같은 실행 안에서 두 기능을 끈 경우의 중앙값은 **19.61 코어 FPS**, 모두 켠 경우는
**21.63 코어 FPS**로 약 **10.3%** 개선됐습니다. 두 기능을 기본으로 켜 두었습니다.

이 장면의 게임 자체 프레임은 약 10.81 FPS이고 에뮬레이션 속도는 정상의 약 36.1%입니다.
개선은 확인됐지만 광장이 정상 속도로 실행되는 수준은 아닙니다.

## 적용 및 사용

현재 테스트 탭과 8081 서버에 수정 코어를 반영했습니다. 새로 실행할 때도 적용됩니다.
기존 `Hardware Shaders`, `WebGL Hardware Draw` 설정을 유지하면 됩니다.
이번 최적화를 위한 사용자 옵션이나 설명 패널은 프론트엔드에 추가하지 않았습니다.

상태 29번은 서버에 그대로 있습니다. 추가 상태 캡처 없이, 게임을 일반 부팅한 뒤
RomM의 `Load Latest State`로 불러왔습니다. 측정 중에는 캐릭터를 움직이지 않았습니다.

## 변경 내용

### 1. 동일한 GPU 업로드 재사용

정점, 인덱스, uniform 데이터가 GPU 버퍼에 아직 남아 있고 새 데이터와 같으면 해당 범위를
다시 사용합니다. 해시는 후보를 찾는 용도이며, 전체 바이트도 비교합니다. 버퍼가 커지거나
처음으로 되돌아가 기존 공간을 덮어쓸 때는 재사용 기록을 지웁니다.

uniform은 세 바인딩별로 별도 버퍼를 사용합니다. 한 버퍼가 순환해도 다른 uniform 블록이
사라지지 않도록 했으며, 바인딩 범위가 그대로이면 중복 설정도 생략합니다.
그리기 순서와 서로 다른 오브젝트의 그리기 호출을 합치지는 않았습니다.

광장에서는 재사용 조회 기준으로 정점 약 **94.1%**, 인덱스 약 **97.7%**, uniform 약
**25.0%**가 일치했습니다. 이는 조회 건수 비율이며 전송 바이트 절감률과는 다릅니다.
큰 데이터가 매번 바뀌면 계속 업로드합니다. CPU 측 복사와 비교 비용도 남습니다.

### 2. WebGL 호출 경로 단축

WebGL 직접 호출용 진입점 37개를 정의하고 자주 쓰는 GL 호출에 적용했습니다.
기존 함수 포인터 조회와 JavaScript 호출 래퍼를 거치는 비용을 줄이는 변경입니다.
렌더러 상태 변경, 스트림 버퍼 업로드, 주요 그리기 경로에 적용했습니다.

상태 저장과 오디오 등에 필요한 Asyncify와 C++ 예외 처리는 유지합니다.
ARM 인터프리터 변경이나 정점 셰이더 비동기화는 이번 범위에 포함하지 않았습니다.

### 준비된 전용 셰이더의 반복 처리 생략

전용 VS/FS 프로그램이 준비돼 있으면 범용 셰이더 설정 계산과 프로그램 준비를 생략합니다.
준비 중인 프로그램의 확인은 필요한 그리기와 프레임 단위에서 진행합니다.
새 픽셀 셰이더를 기다리는 동안 범용 셰이더로 그리는 기능은 유지했습니다.

## 광장 비교 결과

동일 코어·동일 브라우저 실행에서 `끄기 → 둘 다 → 끄기 → 업로드만 → 직접 호출만 → 둘 다`
순서로 비교했습니다. 각 구간은 10초 준비 후 15개의 새 측정값을 기록했습니다.
반복된 설정은 총 30개 측정값의 중앙값입니다. CPU 프로파일러와 GL 타이밍 후크를
제거했고, 측정 중에는 빌드나 다른 GPU 검사를 실행하지 않았습니다.

| 설정 | 코어 FPS | 게임 FPS | 코어 실행 시간 | 그래픽 명령 처리 시간 |
| --- | ---: | ---: | ---: | ---: |
| 두 최적화 끄기 | 19.61 | 9.80 | 46.89 ms | 30.91 ms |
| 업로드 재사용만 | 20.85 | 10.42 | 44.35 ms | 27.82 ms |
| 직접 호출만 | 20.00 | 9.99 | 45.92 ms | 29.81 ms |
| **둘 다 적용** | **21.63** | **10.81** | **42.64 ms** | **25.88 ms** |

표의 모든 설정에는 준비된 전용 셰이더의 반복 처리 생략이 공통으로 들어 있습니다.
따라서 약 10.3%는 그 변경까지 합친 전체 효과가 아니라, 같은 코어에서 두 기능을 켠 효과입니다.
NPC 애니메이션은 계속 진행되므로 프레임 단위로 완전히 동일한 입력을 재생한 시험은 아닙니다.
직접 호출 단독 효과는 작아 장면·기기별 차이가 있을 수 있습니다.

`그래픽 명령 처리 시간`은 에뮬레이터가 그래픽 명령을 처리하는 CPU 경과 시간입니다.
물리 GPU 실행 시간으로 해석하면 안 됩니다. 화면에 표시되는 EmulatorJS FPS와도
구분해서 기록했습니다.

이전 이미지도 상태 29번에서 확인했습니다. 범용 셰이더 도입 전 캐시 코어는 19.76 FPS,
기존 비동기 R2 코어는 17.66 FPS였습니다. 다만 캐시 초기 상태와 하단 화면 캡처 결과가
달라, 이 두 값으로 범용 셰이더의 비용을 정확히 분리할 수는 없습니다.

## 로딩과 화면 확인

수정 코어에서 상태 복원 후 새 비동기 프로그램 **17개 완료, 실패 0개**, 범용 그리기
**152회**를 확인했습니다. 광장 성능 비교 구간에서는 추가 범용 그리기와 대기 프로그램이
모두 0이었으며 기록된 오류도 없었습니다. 로딩 완화 경로를 유지한 상태의 측정입니다.

최초 정점 셰이더 컴파일과 해당 정점의 범용 프로그램 연결은 여전히 동기 방식입니다.
이번 작업에서는 처음 방문하는 다른 맵의 로딩 시간을 다시 비교하지 않았습니다.

일부 스크린샷에는 하단 화면이 검게 찍혔습니다. 이전 캐시 코어와 수정 코어의 여러 설정에서
나타났고, 같은 설정의 다른 캡처에서는 정상적으로 보였습니다. 최종 두 기능 적용 캡처에서는
상·하단 화면이 모두 보였습니다. 이 캡처·표시 현상의 원인과 해결 여부는 이번 시험으로
확정하지 않았으며, 두 기능의 화면 검증이 모든 장면을 보장하는 것은 아닙니다.

## 검증과 재현

- 실제 스트림 버퍼 코드의 정렬, 부분 업로드, 순환, 확장, 재사용, 해시 버킷 충돌,
  캐시·일반 업로드 혼용 검사를 네이티브 ASan/UBSan 및 Wasm에서 통과했습니다.
- 분리된 Chrome WebGL2 컨텍스트에서 실제 GLAD 호출과 직접 호출, 일반 업로드와 재사용을
  조합해 **2,048회** 그렸습니다. GPU에서 읽은 정점·인덱스·uniform 적용 결과가 예상값과
  일치했고 GL 오류가 없었습니다. 버퍼 순환과 재사용 적중·미적중을 모두 포함합니다.
- 전체 코어 빌드, 압축 해제, Wasm 검증, JavaScript 문법, 패치 역적용 검사,
  RomM의 Azahar 런타임 검사, HTTP 다운로드 해시 확인을 통과했습니다.

재현 도구:

- `build/tools/test-azahar-hotpaths.sh`
- `build/tools/test-azahar-webgl-submission.sh` — 출력하는 검증 JS를 별도 WebGL2 탭에서 실행
- `node --test romm/custom-emulatorjs/tests/azahar-runtime.test.cjs`

개발용 비교 값은 `globalThis.__AZAHAR_SUBMISSION_MODE__`입니다. `0`은 둘 다 끄기,
`1`은 재사용, `2`는 직접 호출, `3`은 둘 다입니다. 값을 지우거나 새로 실행하면 기본값 3을
사용합니다. 비교 후 임시 지정은 제거했습니다. 이 값은 사용자 설정으로 저장하지 않습니다.
